# 硬件必要性验证

把“该不该做这台设备”改写成一个可比较的任务，最后给出继续打样、先验证一个环节或暂缓的理由。

## 先复原用户今天的做法

选定一个真实使用场景，写清谁操作、谁受益、谁付费，以及任务何时开始、完成的标志是什么。能引用的原话或观察保留出处。用户设想、供应商宣称与实测分别标记。多种场景分别判断。

建立公平的对照。复原用户手头最顺手的现成方案，例如手机配件、桌面软件、人工记录或专用旧设备。包括设置、现场操作、失败补救、转存与回头查找。记录任务频次和当前做法的摩擦；稀少但代价高的失败也可能支持专用设备。

## 找出只有改变形态才能改善的环节

| 环节 | 当前做法 | 拟议硬件 | 如何证明差异 |
| --- | --- | --- | --- |
| 输入 | 现有设备能捕获什么，在哪个条件下失效 | 传感器、位置、按键或持续佩戴具体多取得什么 | 在相同场景复现问题 |
| 处理 | 现有软件能否产出同类结果 | 设备、手机或云各自承担哪步 | 控制算法、输入或设置，隔离形态贡献 |
| 输出与行动 | 用户现在在哪个工具完成决定 | 谁看到、听到或摸到什么信号，随后实际做什么 | 对照完成率、耗时、错误或中断 |
| 使用负担 | 当前购置、配置、携带与维护 | 新增哪些接线、充电、校准、延迟或学习成本 | 把首次设置和重复使用分开记录 |

如果新增价值主要来自处理流程，可先用现有输入设备或软件模拟结果。若主张依赖传感器位置、时延、触感或免手操作，优先用能复现该差异的廉价原型。把仍无法用替身验证的部分列在结论里。

## 输出一项能改变决定的实验

用一句话给出当前结论和最大不确定性。实验卡写明目标用户、同一任务、基线、试验方案、观察指标、使用负担、成功或停止条件。尽量让同一参与者体验两种方案并平衡顺序。阈值来自用户要求、既有基线或可接受成本；自行拟定时标记为待确认假设。概念兴趣、可用性、实际付费分别记录。

**虚构示例**  
某排练室考虑为音乐教师做一枚脚踏键，踩一下就能在课后录音中定位到学生需要重练的段落。基线为手机录音 App 的现有打点按钮，两组采用相同的录音与检索软件。用现成蓝牙脚踏键模拟新硬件，在相似的谱段教学中轮换两种操作。主指标是课后在规定时间内找回指定片段的比例，另记演奏中断、误触及首次配对耗时。如果手机和脚踏的找回率相近，先查是否只需改进软件索引；若脚踏能稳定减少中断，且反复使用收益覆盖配对负担，再进入定制打样。这一试验支持形态选择，售价仍需独立验证。
