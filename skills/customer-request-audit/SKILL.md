# 用户需求逐条审核

用户问“有多少人在求购”“给谁买、想买什么”时，先确定统计单位。同一个人可以提出多次独立请求；报告“人数”需要可核实的用户标识。只有事件级证据时，报告独立请求数，并说明覆盖的来源和时间窗。

## 从原话识别事件

1. **定义纳入条件。** 按问题写一句可以逐条判断的定义。例如研究送礼需求时，可采用“发言者正在为具体对象挑选礼物，并表达求助或选择意向”。无需已经想到具体商品。本人愿望、旁人推荐和已购体验可以另行分析；信息不足的条目标记为待定。
2. **保留来源角色。** 为原文保留来源 ID、父帖或访谈 ID、时间和可定位的引文。区分发起人补充、旁人建议、另起请求。来源没有稳定链接时使用输入行号或记录 ID。摘录只保留支撑判断所需的文字。
3. **按同一次决策归并。** 删除重复导入记录，把同一人对同一次购买的追问和补充挂到同一事件。回复里也可能有人为自己另行求助。同一作者、父帖或相似措辞都不足以单独证明是同一次需求。跨来源只有在转帖标记、原文链接等证据充分时才合并；无法确认的重合保留标记。
4. **提取可证明的标签。** 从该请求者本人的表达填写对象、场合、预算和明确候选；缺失写“未说明”。他人推荐可保存在独立字段。分类允许多选时，每个事件对同一标签只计一次。保留原始细类与合并关系，便于重算。

## 交付与验收

给出事件明细，至少含事件 ID、来源定位、审核状态、标签和依据。汇总同时列出原始记录数、去重来源数、确认请求数，以及有明确候选的请求数。每张表在表头注明分母；例如“全体确认请求中有多少给朋友”和“给朋友且有明确候选的请求中有多少考虑书籍”使用不同分母。多选占比之和可以超过 100%。样本来自定向检索或单一社区时，将结论限定在该样本内。

扩样时把新增材料与已有事件重新关联，保留稳定的事件 ID，并随审核结果更新所有相关分母和交叉表。交付前从明细重算一次总数，核对候选子集和原话。还有未审记录时，明确已审覆盖率。

## 合成验收例

按上面的送礼定义，审核下面六条输入。

| 输入 | 来源与内容 |
| --- | --- |
| 1 | 帖 A，甲：“想给妹妹挑生日礼物，有建议吗？” |
| 2 | 帖 A，甲补充：“我在书和桌游之间犹豫。” |
| 3 | 帖 A，乙回复甲：“我推荐杯子。” |
| 4 | 帖 A，丙：“借楼问，我也在给同事选离职礼物，完全没头绪。” |
| 5 | 帖 B，丁：“最近大家聊送礼挺多。” |
| 6 | 与输入 1 的来源 ID、正文完全相同，重复导入。 |

**验收结果**应为 6 条输入、5 条去重来源记录、2 个独立选礼请求（甲、丙），其中 1 个有明确候选（甲）。书和桌游在“有明确候选的请求”中各占 1/1，在“全部确认请求”中各占 1/2。点开甲的事件应能定位输入 1 和 2。杯子只出现在乙的建议中。只要改动归并规则或分类规则，就用这个样例检查上述结果。
